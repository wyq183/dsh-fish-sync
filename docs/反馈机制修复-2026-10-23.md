# 同步插件反馈机制修复记录（2026-10-23）

> 主人原话：「同步插件好像你还没做好哦，一直有问题，而且点按钮同步成功没有也不会弹提示
> 也没有进度提示，只有连接失败会有提示」
>
> 这句话里有**四件事**。当成一个「没做好」去修，必然修歪。

---

## 一、先拆：四件事，四条判据

| # | 症状 | 根因 | 判据（怎么确认修好了） |
|---|---|---|---|
| ① | 自动同步从没跑过 | 守卫只看 `cfg.peer`，配对地址在 `runtime.peer` | `/api/state` 的 `lastSyncAt` 不再是 `null` |
| ② | 成功没提示 | 成功分支只 `refresh()`，没有可见反馈 | 面板出现绿色「同步完成 · 推 N / 拉 N」 |
| ③ | 没有进度 | 一次 HTTP 请求，中间状态拿不到 | 同步中能看到「已连上对端 → 拉取 xxx · 1.2 秒」 |
| ④ | 失败可能显示成功 | `syncNow` 拿上一次的旧报告 | 没对端时返回 `ok:false` + 具体原因 |

**①是「一直有问题」的真身** —— 它不是「同步失败」，是「同步从来没开始」。
另外三条是「看起来没反应」的观感问题。

## 二、逐条修

### ① 守卫看错字段（最关键）

```js
// 错
if (cfg.autoSync && (cfg.peer !== '' || cfg.discovery)) {
  ctx.effect(() => { /* 注册定时器 */ })
}
```

扫码配对换来的地址存在 `~/.dsh/fish-sync/paired.json` → `runtime.peer`。
配置文件里 `peer` 字段**从来没被写过** → `cfg.peer === ''` 恒成立。
`discovery` 默认 `false`（2026-10-22 主人定的，广播会泄露设备名）。

→ `'' !== ''` 为 false、`false` 为 false → **整个条件恒假** → 定时器一次都没注册。

**实证**：`GET /ext/fish-sync/api/state` 返回 `lastSyncAt: null`、`discovered: []`。

```js
// 对
if (cfg.autoSync) { ... }
```

守卫只管「要不要开自动同步」。有没有对端交给 `runSync` 内部判：

```js
async function runSync(reason) {
  if (effectivePeer() === '' && !cfg.discovery) return false  // 空转无害
  ...
  return true
}
```

这样配对完成（`loadPaired` 异步读完盘）之后，下一次触发自然就能连上。

### ② 成功要看得见

```js
// 错
post("/api/sync").then(function (j) {
  if (j && j.ok) refresh();
  else alert("同步失败：" + (j && j.error ? j.error : "未知"));
});
```

成功和「什么都没发生」在界面上完全一样 —— 这就是主人说的「只有连接失败会有提示」。

改成面板内状态条（不用 `alert`，Electron / 移动端体验差）：

```
同步完成 · 推 1 · 拉 0 · 跳过 3 · 86 毫秒
```

### ③ 进度：宿主出阶段，前端只显示

同步是一次 HTTP 请求，前端拿不到中间态。**别在前端猜阶段**，让宿主把阶段写进 state：

```js
// lib/index.js —— 把 sync.js 的日志翻成阶段
const stageFromLog = (msg) => {
  const gotManifest = /^对端 (.+?)（.+?）清单 (\d+) 个文件/.exec(msg)
  if (gotManifest !== null) {
    stage(`已连上「${gotManifest[1]}」，对端 ${gotManifest[2]} 个文件`)
    return
  }
  const moved = /^(拉取|推送) (\S+?)(（.*）)?$/.exec(msg)
  if (moved !== null) {
    stage(`${moved[1]} ${moved[2]}`)
    return
  }
  if (/^同步完成：/.test(msg)) stage('完成')
}
```

**认不出的日志就不动阶段** —— 猜阶段是假进度，宁可停在上一个真阶段上。

`state.syncing` 形状：

```js
{ active: true, stage: '拉取 yiqishard/memory/2026-10-23.md',
  reason: '手动', startedAt: '...', elapsedMs: 1234 }
```

结束后**不清空**，只把 `active` 置 false —— 前端要读最后一帧才知道「结束了」。

前端每 500ms 轮询 `/api/state`，配一条 CSS 跑马灯：

```css
.dfs-status.dfs-busy::after {
  content:''; display:block; height:2px; margin-top:7px;
  background: linear-gradient(90deg,transparent,rgba(77,163,255,.9),transparent);
  background-size: 200% 100%;
  animation: dfs-sweep 1.1s linear infinite;
}
```

静止的文案骗不了人 —— 「看起来在动」本身就是反馈。

### ④ 不许拿旧报告冒充

```js
// 错
async syncNow() {
  await runSync('手动')        // 没对端时直接 return，不产生新报告
  const r = state.lastReport   // 读到的是上一次的
  return { ok: r.ok, ... }     // 可能「明明失败却显示成功」
}
```

```js
// 对
async syncNow() {
  if (effectivePeer() === '' && !cfg.discovery) {
    return { ok: false, error: '还没配对：先点「生成配对码」，在另一端输入它', ... }
  }
  const ran = await runSync('手动')
  if (ran === false) return { ok: false, error: '没有可连的对端地址，也没开自动发现', ... }
  ...
}
```

**错误信息要能指导下一步动作** —— 「未知」「失败」等于没报。

## 三、顺带解决：地址失效怎么自救

对端记的是 `192.168.1.10:3098`，实测 ping 不通（ARP 表里只剩 `.1 .3 .5 .6`）。
而这台机器同时挂两个网段：`192.168.1.12`（以太网）和 `192.168.1.14`（无线）。

**只显示一个地址，主人重新配对时很可能填错。** 所以 state 里给全部：

```js
lanAddresses: pickLanAddresses().map((ip) => `${ip}:${cfg.port}`)
// → ["192.168.1.12:3098", "192.168.1.14:3098"]
```

面板上直接列出来：「本机地址 192.168.1.12:3098 或 192.168.1.14:3098（在另一端填这个）」。

## 四、验证（不靠「看起来对了」）

新增 `test/progress.mjs`，7 条用例，**每条都能在旧代码上失败**：

```
── ① 自动同步必须真的被注册（守卫回归）──
  ✅ 🔴 配对地址在 runtime.peer、cfg.peer 为空时，自动同步也要注册
  ✅ autoSync: false 时不注册定时器（别过度修正）
── ② 没对端时要明确报错，不许拿旧报告冒充 ──
  ✅ 🔴 没对端时 /api/sync 返回 ok:false 且说清原因
── ③ 进度：state.syncing 要能从「进行中」走到「完成」──
  ✅ 🔴 同步跑完后 state 里有 syncing 终态 + 上次时间 + 明细
  ✅ 🔴 失败时终态是「失败」而不是「完成」
── ④ 前端反馈（静态契约，防回退）──
  ✅ 🔴 client.js 有状态条 + 进度轮询 + 成功也提示
  ✅ 🔴 管理页（http.js）也有状态条 + 进度
```

## 五、踩到的两个测试坑

### 坑 1：假 ctx 缺 `effect` → 路由静默不挂

`index.js` 挂路由走 `connectionCtx.effect(() => webServer.register(...))`。
假 ctx 给了 `webServer` 和 `connection` 但**没给 `effect`** →
`connectionCtx.effect is not a function` → 被外层 `try/catch` 吞掉 → 只留一条 warn。

**教训**：`apply` 里所有回调都故意吞异常（插件铁律：绝不抛未捕获异常，否则宿主进程直接死）。
代价是**假 ctx 缺成员时报错被吞，症状变成「东西没挂上」而不是 TypeError**。

→ 写假 ctx 前先看源码里 `xxx.yyy(` 出现了哪些，一个都不能漏。
→ 测试报「东西没挂上」时，**第一反应是假 ctx 不全**。

### 坑 2：mtime 同毫秒 → 判不出谁新

临时目录里两端文件在同一毫秒写完 → `mtimeMs` 完全相同 →
「mtime 大的赢」判不出方向 → 变成拉而不是推。

**这是测试环境假象，不是插件 bug。** 测试里要用 `utimes()` 显式造时间差。

## 七、一条更普遍的教训

**「一直有问题」往往不是一个 bug，是好几个独立的静默失败叠在一起。**

先拆成可独立验证的条目，一条一个判据，别急着「整体重写」。
拆不开的时候问自己：**这个症状，能被一条命令验出来吗？** 不能，说明还没拆到底。
